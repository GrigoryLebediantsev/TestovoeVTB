# Архитектура прототипа

Термины — по словарю [CONTEXT.md](../CONTEXT.md), решения — в [docs/adr/](adr). Схема выходных файлов —
в [output-schema.md](output-schema.md).

## Сценарий целиком

```
оператор: python -m src.main
   │
   ▼
main.py ── читает .env, проверяет период, открывает браузер, собирает зависимости
   │
   ▼
controller/cli.py ── аргументы → вход сценария → вызов сценария → итог в консоль и код завершения
   │
   ▼
usecase extract_statement
   1. согласие клиента ─────────────── ClientWindow (BrowserWindow): страница во вкладке клиента
   2. ожидание входа клиента ────────┐
   3. список продуктов               │
   4. по каждому продукту:           ├─ Bank (DemoBank): та же вкладка, кабинет банка
      карточка → история операций ───┘
   5. отбор по периоду, пометка дубликатов, отчёт ── чистые функции domain
   6. запись файлов ────────────────── ResultStorage (FileStorage)
   7. итоговая страница ────────────── ClientWindow
```

Клиент всё время видит одну вкладку: согласие → вход в банк → кабинет, по которому ходит прототип → итог.
Если сценарий прерван доменной ошибкой (отказ, таймаут входа, не загрузился список продуктов), клиент видит
страницу «Выписка не сформирована» с причиной, а файлы выписки не пишутся.

## Слои

Код устроен по слоям: внешние слои знают о внутренних, но не наоборот.

| Слой         | Где                         | Что внутри                                                                 |
|--------------|-----------------------------|----------------------------------------------------------------------------|
| `domain`     | `src/domain/`               | Продукт, операция, период, согласие, отчёт; чистые правила: отбор по периоду, дубликаты, маскирование, генерация идентификаторов, оценка качества |
| `dto`        | `src/dto/`                  | Вход и выход сценариев; эти же модели задают форму JSON и колонки CSV      |
| `usecase`    | `src/usecase/`              | Протоколы зависимостей (`Bank`, `ClientWindow`, `ResultStorage`, `StatementFiles`) и сценарии `extract_statement`, `evaluate_statement` |
| `adapter`    | `src/adapter/`              | Реализации протоколов: `DemoBank`, `BrowserWindow`, `FileStorage`, `JsonStatementFiles` |
| `controller` | `src/controller/cli.py`     | Командная строка: разбор аргументов, вывод итога, коды завершения          |
| `shared`     | `shared/`                   | Инфраструктура без предметной области: браузер, логирование, загрузка настроек, точная запись JSON и CSV |
| точка входа  | `src/main.py`, `src/config.py` | Настройки и единственное место, где создаются конкретные классы         |

Сценарий знает только протоколы. Поэтому банк, окно клиента и хранилище меняются, не трогая сценарий и проверки.
Базы данных нет, результат — файлы ([ADR 0001](adr/0001-no-database-file-output.md)). Оценке качества не нужны
браузер и `.env`, поэтому у неё свой контейнер сценариев ([ADR 0005](adr/0005-evaluation-without-extraction-settings.md)).

## Подключение браузерной сессии

Браузером владеет только `BrowserWindow` (наследник `shared/browser_base.py::BrowserBase`). Адаптер банка получает
его в конструкторе и работает в той же вкладке ([ADR 0004](adr/0004-shared-browser-tab.md)). Подключение и закрытие
вызываются только из `main.py`.

**Режим `launch`** (по умолчанию) — собственный Chromium с окном через Playwright:

- профиль временный (`tempfile.mkdtemp`) и удаляется вместе с cookies после работы; постоянный профиль
  задаётся `BROWSER__PROFILE_DIR`;
- после итоговой страницы прототип ждёт, пока клиент сам закроет окно (`BROWSER__WINDOW_CLOSE_TIMEOUT_SECONDS`),
  и только потом закрывает браузер.

**Режим `cdp`** — подключение к уже открытому Chrome клиента по Chrome DevTools Protocol (`BROWSER__CDP_URL`):

- прототип открывает новую вкладку в первом контексте браузера, то есть рядом с вкладками и cookies клиента;
- при завершении только отключается: браузер и другие вкладки клиента остаются открытыми.

**Страницы прототипа** (согласие, итог, ошибка) создаются прямо во вкладке через `page.set_content`, без
своего веб-сервера. Кнопки «Разрешаю» / «Отказываюсь» пишут решение в атрибут `body`, прототип ждёт его
появления (`BROWSER__CONSENT_TIMEOUT_SECONDS`). Все значения на страницах экранируются.

**Признак входа.** Прототип открывает страницу входа банка и ждёт появления списка продуктов
(`DEMO_BANK__LOGIN_TIMEOUT_SECONDS`). В поля формы входа он не смотрит и ничего в них не вводит. Не дождался —
`LoginTimeout`, данные не читаются.

## Поиск страниц и элементов

- **Все селекторы и подписи кабинета — в одном файле** `src/adapter/demo_bank/selectors.py`: пути страниц,
  CSS-селекторы, подписи полей карточки продукта («Номер карты», «БИК»…), колонки файла экспорта, адрес запросов
  истории. При изменении разметки правится только он.
- Селекторы опираются на устойчивые признаки: `data-testid`, состояния `data-state="ready" | "error"`, подписи полей
  (`dt` → `dd`), а не на порядок элементов.
- Страница продукта читается как набор пар «подпись → значение»: новое поле в кабинете ничего не ломает,
  пропавшее необязательное поле даёт `null`.
- Прототип ходит по кабинету как клиент: открывает страницы по адресам из списка продуктов, выставляет фильтр
  периода в форме кабинета, нажимает «Показать ещё», прокручивает, переходит по страницам истории.
- Каждое ожидание ограничено `DEMO_BANK__ACTION_TIMEOUT_SECONDS`. Технический сбой (таймаут, ответ 5xx, кабинет
  показал ошибку загрузки) повторяется до `DEMO_BANK__RETRY_COUNT` раз; история, загруженная только после
  повтора, даёт предупреждение в отчёте. Незнакомый формат не повторяется: повтор его не исправит.
- Сбой одного продукта не останавливает остальные: продукт получает статус `failed` с причиной.
  Защиты от бесконечной подгрузки — не больше 200 порций или страниц, после этого продукт `partial`.

## Способы извлечения

Для истории каждого продукта способы пробуются по порядку ([ADR 0002](adr/0002-extraction-source-priority.md)):
от самого устойчивого к изменениям интерфейса до самого хрупкого. Использованный способ пишется в отчёт
(`extraction_source`).

1. **Экспорт файла** (`export`). Если на странице есть ссылка «Скачать CSV», прототип нажимает её, как клиент,
   читает скачанный файл и сразу удаляет его с диска. Файл не тот или не скачался — предупреждение и переход
   к следующему способу.
2. **Ответы сервера банка** (`server_response`). Прототип слушает ответы на запросы, которые делает сама
   страница (`page.on('response')`), и **не делает своих запросов к серверу банка**. Если история приходит
   порциями, прототип вызывает следующую так же, как клиент: кнопкой «Показать ещё» или прокруткой вниз.
   Ответы проверяются по схеме (pydantic).
3. **Разбор страницы** (`page`). Строки таблицы операций читаются как текст ячеек; если история разбита
   на страницы с номерами, прототип переходит по ним. Если нет ни строк, ни надписи «Операций нет», это
   изменённая разметка, а не пустая история: продукт получает `failed` с причиной «разметка истории операций
   не распознана», пустая история не выдумывается.

На демо-банке все способы встречаются в одном запуске: у рублёвого счёта есть экспорт (и страницы с номерами),
у долларового счёта история приходит порциями по кнопке «Показать ещё», у карты — при прокрутке, у накопительного
счёта и кредита история только в разметке.

**Фильтр периода.** Если в кабинете есть фильтр, прототип выставляет в нём период, чтобы не загружать лишнее,
и учитывает только ответы сервера за этот период. Нет фильтра — история читается целиком, в отчёте
предупреждение. В обоих случаях операции вне периода затем отбрасываются по тому же правилу, что и у фильтра
кабинета, их число попадает в предупреждения.

## Обработка форматов

Разбор форматов — чистые функции в `src/adapter/demo_bank/parsing.py`. Они проверяются отдельными тестами
без браузера ([ADR 0003](adr/0003-pure-function-tests.md)).

| Что          | Понимает                                                                 | Незнакомое значение                          |
|--------------|---------------------------------------------------------------------------|----------------------------------------------|
| Дата         | `10.06.2026`, `10 июня 2026`, ISO в ответах сервера                       | ошибка формата истории                       |
| Сумма        | `−1 450,00 ₽` (любой минус, пробелы тысяч, неразрывные пробелы), `-1450.00 RUB`, `-1450,00` в экспорте | ошибка формата истории |
| Валюта       | символы `₽ $ €` → ISO 4217, трёхбуквенный код как есть                     | ошибка формата истории                       |
| Статус       | словарь подписей («Проведена», «В обработке», «Отклонена») и кодов сервера | `unknown` + предупреждение с исходной подписью |
| Категория    | словарь подписей                                                          | `other`                                      |
| Тип продукта | словарь подписей                                                          | карточка продукта не загружена               |
| Пустая ячейка | `—` или пусто                                                            | `null`                                       |

Суммы — `Decimal` на всём пути, от разбора до записи файла: в JSON пишутся числом без потери точности
(`shared/json_writer.py`). Нераспознанная дата или сумма не превращается в «примерно правильное» значение:
продукт получает `failed` с причиной «формат истории операций не распознан», остальные продукты извлекаются дальше.
Тексты ошибок разбора не содержат самих значений, поэтому суммы не попадают в лог.

## Проверки выписки

Чистые функции в `src/domain/`:

- **период** — операция относится к периоду по дате проведения, как в фильтре кабинета; у операций в обработке
  и отклонённых даты проведения нет, они относятся к периоду по дате операции;
- **дубликаты** — операция карты, у которой в истории привязанного счёта есть операция с той же датой, суммой
  и валютой, помечается `is_duplicate`; отклонённые не сравниваются, каждая операция счёта — пара не больше чем
  одной операции карты;
- **согласованность** — перед сохранением готовая выписка проверяется: идентификаторы операций не повторяются,
  валюта операции совпадает с валютой продукта, карта ссылается на счёт, который есть в выписке. Нарушения
  попадают в предупреждения отчёта, выписка всё равно сохраняется;
- **идентификаторы** — банковский, если банк его показывает, иначе устойчивый сгенерированный;
- **маскирование** — от номера карты или счёта остаются последние 4 цифры;
- **отчёт** — статус продукта, итоговые количества, `is_complete()` для кода завершения.

## Оценка качества

`python -m src.main evaluate <папка>` сравнивает выписку с эталонной (`demo_bank/reference_statement.json`).
Операции сопоставляются по продукту, дате операции, сумме и валюте. У сопоставленных операций сверяются
нормализованные поля: дата проведения, тип, описание, контрагент, категория, статус. Метрики: точность, полнота,
доля совпавших полей и число предупреждений из отчёта. Эталон берётся только за период выписки.

## Тесты

- **Сквозные** (`tests/test_*_e2e.py`) — главный шов. Поднимается демо-банк и Chromium без окна, прототип
  запускается отдельным процессом в режиме `cdp`, как из командной строки, а тест играет клиента в браузере.
  Проверяются режимы демо-банка, форматы файлов, коды завершения, отказ и таймауты, отсутствие чувствительных
  данных в логе и отчёте.
- **Чистые функции** — разбор форматов и проверки `domain`.
- Тесты и демо проходят в Docker; демо без окна — скрипт поверх тестовых помощников
  ([ADR 0006](adr/0006-headless-demo-and-single-docker-image.md)). Тестовый «браузер клиента» запускается с `--no-sandbox`: в контейнере песочнице
  Chromium не хватает прав, а браузер, который запускает сам Playwright, по умолчанию работает так же.

## Ограничения

- **Один банк.** Реализован только адаптер демо-банка. Для настоящего банка нужен свой адаптер: селекторы,
  словари подписей, форматы.
- **Только русский интерфейс.** Подписи полей, статусов, категорий и названия месяцев — русские словари.
- **Признак входа — появление списка продуктов.** Капча, дополнительная проверка после входа или окончание сессии
  посреди работы не распознаются отдельно: прототип увидит их как таймаут или ошибку загрузки.
- **Последовательный обход в одной вкладке.** Продукты читаются по очереди; для десятков продуктов с длинной
  историей запуск будет долгим.
- **Дубликаты по дате, сумме и валюте.** Две одинаковые покупки за день на карте и на счёте сопоставятся
  правильно по количеству, но какая именно с какой — не гарантируется. Если банк проводит операцию по счёту
  другой датой, дубликат не будет найден.
- **Сгенерированный идентификатор зависит от описания.** Если банк поменяет текст описания операции,
  её идентификатор между запусками изменится.
- **Операция в обработке на границе периода может попасть в две выписки.** Пока она не проведена, она относится
  к периоду по дате операции; после проведения — по дате проведения. Покупка 30.06, проведённая 01.07, будет
  в июньской выписке со статусом «в обработке» и в июльской — со статусом «проведена».
- **Даты без времени и часового пояса**, как их показывает кабинет.
- **Собственный браузер только с окном.** Режим `launch` всегда показывает окно: клиенту нужно войти самому.
  Демо в Docker обходится без окна, потому что действия клиента там выполняет скрипт.
- **Режим `cdp` требует заранее запущенного Chrome с портом отладки**, а с Chrome 136 — с отдельной папкой
  профиля. Обычный уже открытый Chrome без этого подключить нельзя.
- **Нет докачки.** Повторный запуск извлекает всё заново в новую папку.

## Риски поддержки при изменении интерфейса банка

| Что изменилось в кабинете                     | Что произойдёт                                                     | Что править                         |
|-----------------------------------------------|--------------------------------------------------------------------|-------------------------------------|
| Классы и атрибуты разметки                    | Способ «разбор страницы» не найдёт таблицу → `failed` с понятной причиной, а не пустая история | `selectors.py` |
| Разметка, но экспорт или запросы страницы те же | Ничего: история берётся экспортом или из ответов сервера          | —                                   |
| Формат дат или сумм                           | Знакомые варианты распознаются; новый → `failed`, «формат не распознан» | шаблоны в `parsing.py`        |
| Новый статус операции                         | `unknown` + предупреждение с исходной подписью                     | словарь статусов в `parsing.py`     |
| Новая категория                               | `other`                                                            | словарь категорий                   |
| Колонки файла экспорта                        | Экспорт отклоняется, прототип переходит к следующему способу, в отчёте предупреждение | `selectors.py`     |
| Формат ответов сервера                        | Ответ не проходит проверку схемы → `failed`, «формат не распознан» | модели ответа в `parsing.py`        |
| Пропал фильтр периода                         | История читается целиком, лишнее отбрасывается, предупреждение     | `selectors.py`                      |
| Страница входа или признак входа              | Таймаут входа, код 1, ничего не прочитано                          | `selectors.py`                      |
| Подписи полей карточки                        | Поле станет `null`; пропал «Тип» или все суммы — карточка `failed`  | `selectors.py`                      |

Принцип: изменение интерфейса должно приводить к явному предупреждению или ошибке в отчёте, а не к тихой порче
данных. Отчёт о полноте и код завершения `2` позволяют заметить деградацию автоматически, а `evaluate` на демо-банке —
проверить качество после правок. Режимы демо-банка `changed_format`, `changed_layout` и `no_period_filter` воспроизводят
такие изменения в тестах.

## Безопасность и приватность

**Согласие.** Перед каждым запуском клиент видит банк, период и список данных и сам нажимает «Разрешаю». Отказ
или отсутствие ответа завершают программу до открытия кабинета. Время и объём согласия пишутся в отчёт.

**Учётные данные.** Логин, пароль и одноразовый код клиент вводит сам на странице банка. Прототип не читает поля
формы входа, не перехватывает запросы входа (слушает только ответы с историей операций) и не сохраняет cookies:
временный профиль браузера удаляется после работы. В `.env` нет секретов банка.

**Без обхода защиты.** Прототип не делает своих запросов к серверу банка, а только читает то, что страница
получила сама, и действует в кабинете как клиент. Капча и подтверждения остаются за клиентом.

**Минимум данных.** Читается только то, что перечислено в согласии. ФИО клиента не извлекается, хотя видно
на странице. Полный номер карты маскируется сразу при разборе и не сохраняется нигде. Номер счёта сохраняется
в реквизитах: он нужен потребителю выписки для расчётов.

**Логи и отчёт.** В лог и `extraction_report.json` попадают только идентификаторы продуктов и операций,
маскированные номера и количества: ни сумм, ни описаний, ни контрагентов, ни полных номеров. Тексты ошибок разбора
не содержат значений. Это проверяет сквозной тест `test_sensitive_data_e2e.py`. Итоговая страница в браузере
показывает только количества и предупреждения отчёта.

**Файлы.** Скачанный экспорт удаляется сразу после чтения. Файлы выписки содержат финансовые данные клиента
и пишутся только локально в `STORAGE__OUTPUT_DIR`; папка `output/` исключена из git. Прототип никуда их
не отправляет. Хранение и передача файлов — ответственность того, кто их использует.

**Браузер клиента.** В режиме `cdp` прототип работает в отдельной новой вкладке и не закрывает браузер и чужие
вкладки.

**Docker.** Контейнер работает от обычного пользователя `pwuser`, а не от root. Chromium в контейнере работает
без песочницы: это допустимо для локального демо-банка, но настоящий кабинет банка клиент должен открывать
в своём браузере на своей машине.

## Масштабирование на несколько банков

Сценарий, проверки, отчёт и форматы файлов от банка не зависят: сценарий работает с протоколом `Bank`
из `src/usecase/__init__.py`:

```python
class Bank(typing.Protocol):
    display_name: str
    async def wait_for_login(self) -> None: ...
    async def get_product_ids(self) -> list[str]: ...
    async def get_product(self, product_id: str) -> domain.Product: ...
    async def get_transactions(self, product_id: str, period: domain.Period) -> domain.TransactionHistory: ...
```

Новый банк — новый адаптер по образцу `src/adapter/demo_bank/`:

1. `src/adapter/<bank>/selectors.py` — адреса, селекторы и подписи кабинета.
2. `src/adapter/<bank>/parsing.py` — словари статусов, категорий, типов продуктов, форматы дат и сумм,
   разбор экспорта и ответов сервера. Это чистые функции: их можно проверить тестами на образцах без браузера.
3. `src/adapter/<bank>/<bank>.py` — класс, реализующий `Bank`: какие способы извлечения есть у этого банка
   и в каком порядке их пробовать. Ошибки — доменные (`ProductDetailsNotLoaded`, `TransactionsNotLoaded`…),
   чтобы сценарий единообразно помечал продукт `failed`.
4. `src/adapter/<bank>/config.py` — адрес кабинета, таймауты, число повторов.
5. Значение в `BankName` и раздел настроек в `src/config.py`, ветка в `main.py::create_bank`.

Выбор банка — настройка `EXTRACTION__BANK` в `.env`, код сценария при этом не меняется. Другой язык интерфейса
того же банка — другие словари и шаблоны в `parsing.py`.

Что ещё понадобится при росте:

- **Общая часть адаптеров.** Порядок способов, повторы и ожидание ответов страницы сейчас живут в `DemoBank`.
  Когда появится второй банк, общую механику стоит вынести в базовый класс в `shared/`, а в адаптерах оставить
  только селекторы, форматы и набор способов.
- **Несколько банков за один запуск** — цикл по банкам в контроллере с отдельным согласием и входом
  для каждого; выписка остаётся «один банк — одна папка».
- **Проверка на эталоне** — для каждого банка свой набор образцов экспорта, ответов и страниц и эталонная выписка,
  чтобы `evaluate` и тесты разбора ловили изменения интерфейса.
